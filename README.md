# OntoStart

OntoStart publishes FAIR (Findable, Accessible, Interoperable, Reusable) OWL ontologies with GitHub Actions. This repository holds two things:

* the **engine**: the Python package `ontostart` (`src/ontostart/`) and the reusable workflows `build.yml` and `w3id-pr.yml`, released as tags `v1`, `v1.1`, `v1.2`, ... (see [Engine releases](#engine-releases))
* the **collection**: Michel Dumontier's ontologies, one folder each, built by the engine.

What you get for every ontology:

* a w3id.org persistent identifier, with versioned IRIs
* content-type negotiation to get the ontology in different syntaxes
* rich ontology metadata, as per the FAIR principles
* GitHub Actions that check the OWL 2 DL profile and consistency (ROBOT with HermiT), bump the version on commit, write Turtle, RDF/XML, JSON-LD and N-Triples files, generate documentation (OntoSpy and pyLODE), run a FOOPS! FAIRness assessment, and publish a website to GitHub Pages

To publish your own collection under your own w3id.org identifier, see [Start your own collection](#start-your-own-collection).

## The collection

The site's front page, <https://w3id.org/ontostart/> (<https://micheldumontier.github.io/ontostart/>), introduces OntoStart; its source is [`site/index.html`](site/index.html). The ontologies are listed in the catalogue at **<https://micheldumontier.github.io/ontostart/catalog/>**, with each one's version, description, IRI and source folder. CI regenerates the catalogue every time it publishes, so a new ontology or sandbox entry appears there without editing this README. The same list is available as DCAT in `catalog.ttl`, `catalog.jsonld`, `catalog.nt` and `catalog.owl` (stable and experimental ontologies only).

The status of an ontology decides its section in the catalogue:

* **stable**: the default for folders under `ontologies/`.
* **experimental**: set in `ontostart.yaml`; the site shows a banner. `suloized-pizza` is generated by ontointegrator from the Manchester Pizza ontology.
* **sandbox**: every folder under `sandbox/`; tutorial ontologies, not persistent, may be removed. `testo` is the example to copy.

Retrieve the ontology in different syntaxes, or a specific version:

```
curl -L -H "Accept: text/turtle" https://w3id.org/ontostart/pizza/
curl -L -H "Accept: application/rdf+xml" https://w3id.org/ontostart/pizza/
curl -L -H "Accept: application/ld+json" https://w3id.org/ontostart/pizza/
curl -L -H "Accept: application/n-triples" https://w3id.org/ontostart/pizza/
curl -L -H "Accept: text/turtle" https://w3id.org/ontostart/pizza/1.0.1
curl -L https://w3id.org/ontostart/pizza/BakingDuration    # term page in a browser
```

The retired root ontology `ontostart.ttl` is archived on GitHub Pages under `main/`; its `/x.y.z` IRIs still resolve.

Until November 2026 each ontology lived on its own branch (`pizza`, `pro`, `testo`, `suloized-pizza`). Those branches are kept as the tags `archive/<branch>`; `git checkout -b pizza archive/pizza` restores one.

## Repository layout

```
ontostart.yaml                    collection configuration
ontologies/<name>/<name>.ttl      curated ontology (+ versions/, README.md, optional catalog-v001.xml, imports/)
sandbox/<name>/<name>.ttl         tutorial ontology
apache/web/ontostart/.htaccess    w3id.org redirects, generated by `ontostart htaccess`
apache/tests/redirects.tsv        expected redirects
apache/test-redirects.sh          redirect tester
src/ontostart/, tests/            the engine and its tests
.github/workflows/                build.yml, ontostart.yml, w3id-pr.yml, engine-tests.yml
docs/classroom.md                 how students publish a sandbox ontology
site/index.html                   the site's front page (`home:` in ontostart.yaml)
template/                         content of the ontostart-template repository (see below)
```

`<name>` matches `^[a-z0-9][a-z0-9-]*$`. `sandbox`, `versions`, `docs`, `catalog`, `main` and the keys of `aliases` are reserved.

## What CI does

| Event and ref | Targets | Bump and commit back | Publish |
|---|---|---|---|
| push to `main` | folders with changed files (all, if `ontostart.yaml` changed) | yes | yes |
| push to `sandbox/<name>` | `sandbox/<name>/` only | yes | yes |
| push to `main` that changes only the `home:` page | none | no | the front page only |
| push to any other branch, or pull request (from any branch, `sandbox/<name>` included) | folders with changed files | no | no |
| manual run | one folder or all; the bump is an input (default no) | per input | yes, on `main` and `sandbox/*` |

Per target: OWL DL profile check, HermiT reasoning (using the folder's `catalog-v001.xml` when present), version bump, four syntaxes, OntoSpy and pyLODE docs, FOOPS! (if enabled), site page.

A target is **blocked** (not committed, not published, and the run fails at the end) when the profile check fails, the ontology is inconsistent, reasoning errors, its ontology IRI is not `https://w3id.org/<w3id>/<path>/`, or its unsatisfiable-class count differs from `compare_unsatisfiable_with`. Unsatisfiable classes alone do not block. One run makes at most one commit to the ref and one push to `gh-pages`; runs on the same ref never overlap.

The site is published on the `gh-pages` branch: at the root the front page (`index.html`, or the catalogue page when `home:` is not set) and the DCAT catalogue (`catalog.{ttl,jsonld,nt,owl}`), the catalogue page at `catalog/` when `home:` is set, and, for each ontology, its page, `meta.json`, `versions/`, `docs/` and `foops/`. Set Pages to "Deploy from a branch", `gh-pages`, `/` root.

## `ontostart.yaml`

```yaml
w3id: ontostart                                   # https://w3id.org/ontostart/
pages: https://micheldumontier.github.io/ontostart
gist_id: 9affe51b863c5144fa82d7b1d23449aa         # badges; empty disables them
sandbox: true
foops: true
term_docs: ontospy                                # or "site"
home: site/index.html                             # front page; the catalogue page moves to catalog/
aliases:                                          # old path -> current path
  testo: sandbox/testo
legacy_root:                                      # /x.y.z of the retired root ontology
  path: main
  name: ontostart
ontologies:
  suloized-pizza:
    status: experimental
    compare_unsatisfiable_with: imports/pizza.owl
```

## Publishing a sandbox ontology

Students and workshop participants copy `sandbox/testo/` to `sandbox/<name>/`, rename the file, and open a pull request from their fork; CI checks it, and it is published when the pull request is merged into `main`. Students you trust with write access can instead push a branch `sandbox/<name>`, which publishes on every push. Either way it is published at `https://micheldumontier.github.io/ontostart/sandbox/<name>/`, with the IRI `https://w3id.org/ontostart/sandbox/<name>/`. No w3id.org pull request is needed. See [docs/classroom.md](docs/classroom.md).

## Redirects

`https://w3id.org/ontostart/...` is served by `apache/web/ontostart/.htaccess`:

| Path | Goes to |
|---|---|
| `/` | the catalogue (HTML), or `catalog.<ext>` for RDF requests |
| `/<name>/...`, `/sandbox/<name>/...` | that ontology: the ontology itself, `x.y.z`, `versions/...`, `<file>.<ext>`, `docs`, terms |
| `/testo/...` | alias of `/sandbox/testo/...` |
| `/x.y.z` | the archived root ontology |

The `.htaccess` never lists ontologies, so new ontologies and sandbox entries need no w3id.org pull request.

Regenerate and test it:

```
uv run ontostart htaccess
bash apache/test-redirects.sh                                   # local Apache in Docker
bash apache/test-redirects.sh --targets                         # also check the GitHub Pages targets exist
bash apache/test-redirects.sh --url https://w3id.org/ontostart  # the live redirects
```

## Proposing redirects to w3id.org

Run the `Propose w3id.org redirects` workflow (`w3id-pr.yml`). It tests the redirects and opens a pull request against [perma-id/w3id.org](https://github.com/perma-id/w3id.org/pulls). Before running it, sync your fork of `perma-id/w3id.org` so the pull request is based on current content. The `W3ID_TOKEN` secret is a classic personal access token with the scopes `repo`, `read:org` and `workflow`.

## Secrets and variables

* `GIST_TOKEN` (secret): a fine-grained personal access token with Gists read and write access (or a classic PAT with the `gist` scope), used to write the badge data. Badges are pushed from `main` only.
* The badge gist is a public gist; its id is `gist_id` in `ontostart.yaml`.
* `W3ID_TOKEN` (secret): see above.

Both tokens must be secrets of the environment `ontostart-secrets`, not repository secrets. Anyone with write access can push a branch with a modified workflow and run it, and such a run can read every repository secret; an environment limited to `main` keeps the tokens out of those runs. To set it up: Settings → Environments → New environment `ontostart-secrets` → Deployment branches and tags: Selected branches and tags, add `main`; add `GIST_TOKEN` and `W3ID_TOKEN` as environment secrets; delete the repository-level copies. Only the badges job and `w3id-pr.yml` use that environment. This repository passes them to the reusable workflows with `secrets: inherit`; a collection in another account passes them by name, as the template does.

## Start your own collection

1. On <https://github.com/micheldumontier/ontostart-template>, click **Use this template**. Its first run builds nothing and asks you to run `ontostart init`.
2. In a clone, fill in your w3id.org name, GitHub account and repository:

   ```
   uvx --from git+https://github.com/micheldumontier/ontostart@v1.4 ontostart init --w3id NAME --owner OWNER --repo REPO [--gist GIST_ID]
   ```

   This writes `ontostart.yaml`, the example ontology's IRIs (`https://w3id.org/NAME/testo/`), the w3id workflow, and `apache/web/NAME/.htaccess` with its README. Commit and push: CI builds the example and creates `gh-pages`.
3. Turn on Pages (`gh-pages`, `/` root), create the `ontostart-secrets` environment (see [Secrets and variables](#secrets-and-variables)), and run **Propose w3id.org redirects** to claim `https://w3id.org/NAME/`.

The template's README has the details. Its workflows call this repository's `build.yml` and `w3id-pr.yml` at a fixed release.

## Engine releases

| Tag | Adds |
|---|---|
| `v1` | the engine, reusable build and w3id workflows, collection layout, sandbox |
| `v1.1` | `ontostart init` and the template content in `template/` |
| `v1.2` | a repository created from the template builds nothing until `ontostart init` has run; template pinned to `v1.2` |
| `v1.3` | the catalogue page shows each ontology's IRI and source folder, and what each status means; template pinned to `v1.3` |
| `v1.4` | optional `home:` front page (the catalogue page moves to `catalog/`); editing it republishes only the front page; template pinned to `v1.4` |

A collection pins a release in `.github/workflows/ontostart.yml` and `.github/workflows/w3id-pr.yml`, each in two lines (`uses: ...@vX.Y` and `engine-ref: vX.Y`); change all four together to upgrade. This repository builds with the engine from its own checkout. To release: tag `main` as `vX.Y`, update the pins under `template/`, and push the `template/` content to the template repository.

## Running the engine locally

```
uv run pytest
uv run ontostart --help
uv run ontostart plan --ref main --event workflow_dispatch   # list the build targets
uv run ontostart init --help                                  # set up a repository created from the template
```
